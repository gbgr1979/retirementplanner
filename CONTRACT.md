# Internal contract
Static vanilla ES modules; Node built-in tests; no runtime dependencies.
Plan version 4:
{version:4,drawdown:{mode:'pots'|'totalIncome',annualAmount:0,inflationLinked:true,stages:[]},name,startMonth:'2026-11',endAge:95,includePartner:false,inflation:2.5,scenarioSpread:2,monthlySpending:2500,spendingStart:'2044-11',people:[{id:'you'|'partner',name,dob:'YYYY-MM-DD',retirementMonth:'YYYY-MM',region:'rUK'|'scotland',taxFreeUsed:0}],pots:[{id,name,owner,type:'savings'|'cashIsa'|'stocksIsa'|'sipp'|'workplace',balance,monthlyContribution,employerContribution,contributionBasis:'gross'|'netRelief',growth,fee,contributionStart,contributionEnd,accessAge:57}],incomes:[{id,name,owner,type:'state'|'db'|'other',monthlyAmount,startMonth,endMonth,escalation}],events:[{id,name,month,type:'withdrawal'|'transfer',potId,toPotId:'',amount}]}
Rates in percent per annum. Contributions at month start then growth then charges then events. Monthly contributions are amount entering pot when gross, or net personal /0.8 when netRelief. Employer always gross. Monthly spending in startMonth pounds, inflation indexed; recurring gross withdrawal target starts at primary retirement and removes the remaining monthly target after successful scheduled withdrawals. Spending shortfall is a separate comparison, never a second pot deduction. Annual pension tax estimate allocated across that tax year's income; current 2026/27 rules frozen. Contributions funded externally and not deducted from retirement spending unless clearly reported. Income monthly amount expressed at plan start pounds; escalation annual effective. Events fixed nominal gross removal; transfer only accessible same-owner nonpension pots (no pension transfer or subscription allowance inference).
API src/model.js: export project(plan,{scenario:'base'|'lower'|'higher'}={}), returns {months:[{month,balances:{id:value},accessible,locked,total,incomeGross,incomeNet,withdrawalsGross,withdrawalsNet,tax,spending,shortfall,contributions,growth,fees,warnings:[]}],years:[{year,opening,contributions,growth,fees,withdrawals,closing,incomeGross,incomeNet,spending,shortfall,tax,accessible,locked,balances}],warnings:[],assumptions:[]}. Years are calendar years for charts; tax engine uses Apr-Mar. Transfers not counted as household withdrawals. project never mutates plan. End at primary person endAge bounded max 80 years.
API src/plan.js: export createExamplePlan(), validatePlan(plan) returns {valid,errors}, parsePlan(text) returns validated plan or throws Error; serializePlan(plan) validates and returns JSON text. Strict unknown/prototype keys rejection and limits; names plain text. UI uses textContent/escaped strings not untrusted HTML. Dates valid Gregorian and months regex+range; all references checked. 1MB import max.

Drawdown v4: annualAmount finite0..12000000. InflationLinked anchors plan.startMonth; false means fixed nominal. Monthly actual successful event withdrawals offset target in same month only; transfers/rejected events do not. Remaining target partially draws from accessible savings/cashIsa/stocksIsa/pensions, grouped type then owner you/partner then original list order. No negative balances. In mode 'pots', income remains independent. In mode 'totalIncome', gross active income offsets the gross target before recurring pot withdrawals; the income is still counted once in household income and taxed by owner. Monthly/year fields: incomeTarget (gross combined goal or zero in pots mode), incomeOffset (gross income counted toward combined goal), withdrawalTarget (gross amount required from pots after income offset),scheduledWithdrawalsGross,recurringWithdrawalsGross,unmetWithdrawal; existing withdrawal totals include both. firstUnmetWithdrawal:{month,amount,locked,total,accessible}|null. parsePlan strictly validates each v1, v2 and v3 shape before migration. v1 receives mode 'pots', annualAmount 0 and inflationLinked true; v2 preserves annualAmount and inflationLinked and receives mode 'pots'. v3 preserves all prior values including mode. All legacy versions receive stages:[], without inventing age changes. validatePlan/serialize accept v4 only, requiring mode 'pots' or 'totalIncome' and stages. Incoming v3 missing mode or containing future stages is rejected, never guessed.

Wizard State Pension: draft.you.statePension and draft.partner.statePension each start as {enabled:false,weeklyAmount:'',startMonth:'',escalation:2.5}. No default entitlement or claiming date. At money step index 1, active people with enabled===true require a finite numeric weekly GBP amount 0..10000, explicit supported YYYY-MM claim month not before their approximate birth month, and an editable finite annual escalation assumption 0..15. Disabled forecasts retain draft values but ignore them for validation and building; inactive partners are excluded. Review step 3 includes this validation. Zero forecasts do not create income.
Build creates fresh deterministic state-you/state-partner income rows only for active, opted-in positive forecasts, converting weekly GBP by *52/12 without intermediate rounding. startMonth is the explicit claim month. endMonth is the last inclusive projection month, or 2250-12 for a claim beyond the projection. Income amounts and escalation are anchored to plan.startMonth, not claiming date. Escalation is an assumption, not a guaranteed uprating. The initial drawdown mode is totalIncome when at least one such forecast exists, otherwise pots. annualAmount remains monthlySpending*12 as a gross scenario target, not an after-tax spending guarantee. Back-navigation and rebuilding neither mutate draft data nor duplicate income rows. Exported plan numeric values remain numbers.

Income stages v4: drawdown.stages is a required array with zero to ten entries {fromAge,annualAmount}. fromAge is an integer 18..110, strictly increasing and unique. annualAmount is finite 0..12000000. Empty stages preserve the flat baseline annualAmount. Amounts are gross and share the drawdown mode and inflationLinked choice. Each stage replaces the baseline/previous target from the primary person's first full month on or after that birthday (same month for day 01, next month otherwise), never before the primary retirement month. Already-passed stages activate the latest eligible amount at retirement or projection start. Moving retirement never changes saved ages or amounts. Future stages outside the horizon remain saved but are not applied. A zero stage disables recurring withdrawals for that range, not scheduled events or other income.
All stage amounts, including later changes, use the original plan.startMonth inflation anchor. Total-income gross offsets and successful same-month scheduled withdrawals still apply exactly once. Spending remains a separate net-cash comparison. Partner inclusion changes active pots and incomes, not the age basis. No net-income gross-up, after-tax guarantee or reinvestment is introduced.
API src/income-stages.js accepts validated plans: stageStartMonth(dob,fromAge) returns YYYY-MM; stageIndexAtMonth(plan,month) returns zero-based stage index or -1 for baseline/pre-retirement; annualTargetAtMonth(plan,month) returns unindexed annual amount, zero before retirement. incomeStageRanges(plan) returns effective in-horizon {stageIndex,fromAge:null|number,annualAmount,startMonth,endMonth} ranges, with exclusive endMonth, clamped to projection start/retirement and the same exclusive horizon as project. No helpers mutate inputs. Monthly model rows expose activeAnnualTarget (unindexed annual basis) and stageIndex; neither is summed into annual rows. Existing incomeTarget/withdrawalTarget are monthly nominal flows and continue to aggregate normally.
